## New finding: identical pins selected different agents

Sample 7 is an eastus diagnostic failure, not a reproduced allowed-traffic
failure. Its log shows the TLS-status request timing out after three seconds:

```text
Unable to check TLS_STATUS. Defaulting to TLS enabled.
```

It consequently downloaded the TLS agent v1.9.4 archive, SHA-256:

```text
66f309e8fa41aa6b96a5e740afccefa3b89e90fb62180cdbe73948f3bc068f57
```

The other seven jobs used community agent v0.17.0 archive SHA-256:

```text
e0faa2687554ebd5629595bcd5531360781abe3e2746ef8ce5a030961a3acab0
```

The exact pinned action source corroborates this behavior:
`src/tls-inspect.ts` returns true when its bounded fetch throws, and
`src/checksum.ts` specifies both archive hashes. The retained installed-agent
hashes also differ. This is a demonstrated extra comparison variable; it does
not establish why that status request failed or cause the older westus2 faults.

The TLS agent recorded the control as:

```text
ip address dropped: 172.66.147.243 exe=/usr/bin/curl pid=2752
```

The control’s curl process had PID 2752 and exited 28. The community-format
verifier required an additional exact connection/port event and stayed
UNCONFIRMED. We retained the failed job and did not relax that predicate or
rerun it. Its allowed operations, API read, capture and post steps succeeded.
Do not count this sample as a complete diagnostic pass or conflate it with the
reported allowed-GitHub connection failure. Any parser adaptation would require
a separate exact-source Sol review and must preserve strict evidence standards.

## What the comparison now supports

The later existing westus2 failure used the same community-agent archive as
our seven community samples. Therefore an action/agent-version-only explanation
is insufficient across these observations. The later log also shows checkout
eventually succeeding before the subsequent API call fails: checkout success
alone cannot clear API access or job-completion concerns.

In the seven healthy community samples, the observed Git destinations and API
remote IPs agree with the relevant agent mappings and appear in the frozen DNS
answer sets. Those sets also contain some different pre-hardening answers,
showing why multiple IPs for one hostname are not by themselves proof of a bug.
The older failures matter because the application destination was actually
rejected while differing from the agent’s mapping. We still lack before/after
packet and native-rule evidence from that affected setup.

Static agent-source inspection confirms that community setup already restarts
systemd-resolved and flushes its cache. Recommending another generic cache flush
without identifying the surviving resolver/cache path is unsupported. Native
nftables visibility is now available for a future affected capture, but these
unaffected samples do not identify a redirect to correct.

## Reviewable next step

Stop regional sampling; more random green runners provide little additional
causal evidence. The reviewed probe and receipts are ready for reuse when an
affected setup recurs. Capture the actual region, image, selected agent/hash,
resolver listeners/configuration, native rules and DNS/application/drop sequence.
First retain the failing baseline, then select one narrow counterfactual from
what it shows. Review that exact candidate independently before execution or
rollout. Do not force a different tier, alter the subscription, relax blocking,
allow arbitrary destination IPs or stop runner services as a speculative fix.

A TLS-log parser extension could improve the diagnostic but would not repair
the westus2 outage; it is not required to explain or preserve this sample.
No new workflow dispatch, PR merge, retry allowance or fleet-wide recovery is
implied by these results. Keep existing PR-specific checks and holds separate.
